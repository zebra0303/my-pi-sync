# 개인정보 입력 인식 가드 (PII Awareness Guard)
## 목적
이 Skill은 사용자가 실수로 또는 의도치 않게 민감한 개인정보를 대화에 입력했을 때,
이를 감지하고 처리를 거부함으로써 불필요한 개인정보 노출/처리를 최소화하기 위한
1차 방어선 역할을 한다.
**주의:** 이 Skill은 기술적 DLP(Data Loss Prevention)를 대체하지 않는다.
입력된 텍스트는 이미 시스템 로그/저장소에 기록될 수 있으며, 이 Skill은
Claude의 응답 단계에서의 처리 거부만을 보장한다.
## 감지 대상 패턴

- **주민등록번호 / 외국인등록번호**: 6자리(YYMMDD) + 7자리(성별코드+지역코드+검증숫자)
  형식, 하이픈 포함(123456-1234567) 또는 미포함(1234561234567) 모두 감지.
  앞 6자리(YYMMDD)는 실제 날짜로 유효한 범위일 때만 주민등록번호 패턴으로 판단한다:
  - **MM(월)**: 01~12 범위에 있는 경우만 유효 (정규식 예: `(0[1-9]|1[0-2])`)
  - **DD(일)**: 01~31 범위에 있는 경우만 유효 (정규식 예: `(0[1-9]|[12][0-9]|3[01])`)
  - 전체 조합 정규식 예: `\d{2}(0[1-9]|1[0-2])(0[1-9]|[12][0-9]|3[01])[-]?[1-4]\d{6}`
  - MM 또는 DD가 위 범위를 벗어나는 숫자열(예: `999999-1234567`, `881399-1234567`)은
    날짜로 성립하지 않으므로 주민등록번호 패턴으로 오탐하지 않고, 이 규칙에서는
    감지 대상에서 제외한다. (단, 다른 패턴 — 신용카드번호 등 — 에는 해당할 수 있으므로
    별도로 재검사한다.)

- **여권번호 (대한민국)**: 총 9자리 영숫자 조합, 아래 두 패턴 중 하나와 일치할 때만
  여권번호로 판단한다 (Microsoft Purview의 South Korea Passport Number 정의 기준):
  - **구여권 형식**: `[MSROD]` 1자 + 숫자 8자리 — 정규식 예: `^[MSROD]\d{8}$` (예 구조: M12345678)
  - **차세대 전자여권 형식(2021년~)**: `[MSROD]` 1자 + 숫자 3자리 + 영문 1자 + 숫자 4자리
    — 정규식 예: `^[MSROD]\d{3}[A-Z]\d{4}$` (예 구조: M123A4567)
  - 시작 문자는 여권 종류 코드(M=일반, D=외교관, R=관용/거주 등)이므로 **M, S, R, O, D 중 하나가
    아니면** 여권번호 패턴에서 제외한다 (예: `X12345678`은 감지 대상 아님).
  - 체크섬은 없으므로(공식적으로 검증 숫자가 존재하지 않음), 형식 일치 자체를 근거로 판단하되,
    "여권", "passport", "여권번호" 등 주변 키워드가 함께 있으면 신뢰도를 높게 판단한다.

- **신용카드번호**: 14~19자리 연속 숫자(하이픈/공백으로 4자리씩 구분된 형태 포함).
  아래 조건을 **모두** 만족해야 신용카드번호로 판단한다 (Microsoft Purview Credit card
  number 정의 기준):
  1. 자릿수가 14~19자리 범위
  2. **Luhn 체크섬을 통과**하는 경우만 유효한 카드번호로 판단 (체크섬 불통과 시
     단순 숫자열로 간주하고 감지 대상에서 제외)
  3. 주요 카드사 BIN(시작 번호) 대역과 일치하면 신뢰도 상승: Visa(4로 시작),
     Mastercard(51~55 또는 2221~2720으로 시작), Amex(34, 37로 시작),
     Diners(300~305, 36, 38), Discover(6011, 65), UnionPay(62), JCB(3528~3589)
  4. "카드번호", "CVC", "유효기간", "카드소지자명" 등 주변 키워드가 있으면 신뢰도 상승
  5. 금융기관 테스트/예약용으로 공개된 더미 카드번호(예: 4111-1111-1111-1111 등 결제
     테스트에 공식적으로 쓰이는 번호)는 실제 개인정보가 아니므로 감지에서 제외 가능

- **조합 민감 정보**: 이름 + 전화번호 + 주소가 함께 입력되는 경우
  (개별 항목보다 조합 시 식별 가능성이 높아지므로 민감도 상승으로 판단). 전화번호는
  아래 형식을 기준으로 판단한다:
  - 휴대전화: `01[0|1|6|7|8|9]-?\d{3,4}-?\d{4}` (예 구조: 010-XXXX-XXXX)
  - 유선전화(지역번호 포함): `0(2|3[1-3]|4[1-4]|5[1-5]|6[1-4])-?\d{3,4}-?\d{4}`
  - 주소는 별도 정규식 대신 "시/도 + 구/군 + 도로명 또는 지번" 조합이 함께 등장하는지로
    휴리스틱하게 판단한다 (정형화된 체크섬이 없는 자유 텍스트이므로 100% 정규식 판별은 불가).

## 파일 형식 기반 감지 — DICOM(의료영상) 파일

Lunit 업무 특성상 DICOM 파일에는 환자 식별정보(PHI, Protected Health Information)가
메타데이터 형태로 포함되어 있는 경우가 많으므로, 텍스트 패턴이 아닌 **파일 자체**를
감지 대상으로 별도 취급한다.

- **확장자 기반 감지**: 업로드/첨부된 파일의 확장자가 `.dcm`, `.dicom`, `.dic` 인 경우
  DICOM 파일로 판단한다.
- **매직 바이트(파일 시그니처) 기반 감지**: 확장자가 없거나 다른 확장자로 위장된 경우에도,
  파일 앞부분 **128바이트(프리앰블)** 이후 이어지는 4바이트가 `DICM`
  (헥스: `44 49 43 4D`)이면 DICOM 파일로 판단한다. 파일 내용을 실제로 열어볼 수 있는
  도구(Read, Bash 등)를 사용할 수 있는 상황이라면 확장자보다 이 방식을 우선한다.
- **판단 시 확인하는 PHI 태그(참고용)**: DICOM 표준상 아래 태그들에 환자 식별정보가
  직접 담기는 경우가 많다.
  - (0010,0010) PatientName
  - (0010,0020) PatientID
  - (0010,0030) PatientBirthDate
  - (0010,0040) PatientSex
  - (0008,0050) AccessionNumber
  - (0008,0080) InstitutionName
- **비식별화(익명화) 여부와 무관하게 전면 차단**: (0012,0062) PatientIdentityRemoved
  태그가 `YES`로 확인되더라도 현재는 예외를 두지 않고 동일하게 차단한다. (참고용으로만
  기록 — 추후 비식별화 확인 절차 도입 시 이 항목을 갱신)
- **디렉터리/시리즈 업로드**: 확장자 없이 여러 DICOM 슬라이스가 폴더째로 업로드되는
  경우도 흔하므로, 개별 파일명만으로 판단하지 말고 폴더 내 파일 중 하나라도 위 조건에
  해당하면 전체를 DICOM 세트로 간주한다.

## 감지 시 행동
1. 감지된 개인정보 텍스트를 요청된 작업(요약, 번역, 분석, 문서 작성 등)에
   **사용하지 않는다.**
2. 다음과 같은 형식으로 응답한다:
   > 입력하신 내용에 개인정보(예: 주민등록번호로 추정되는 패턴)가 포함되어 있어
   > 해당 부분은 처리하지 않았습니다. 마스킹 처리 후 다시 입력해 주세요.
   > (예: 901231-1\*\*\*\*\*\*)
3. 감지된 개인정보를 응답에서 **그대로 반복하거나 인용하지 않는다.**
   (패턴이 감지되었다는 사실만 언급하고, 실제 숫자/문자열은 마스킹하거나 생략)
4. 사용자가 "그냥 처리해달라", "이건 테스트 데이터다" 등으로 재요청해도
   동일하게 거부한다. 단, 명백히 예시/포맷 설명 목적의 가상 데이터
   (예: "123-45-6789 형식이 맞나요?")는 실제 개인정보 여부를 판단하여 유연하게 대응한다.
5. 개인정보가 포함된 부분을 제외한 나머지 요청은 정상적으로 처리한다.
   (전체 요청을 거부하는 것이 아니라, 민감 부분만 분리하여 처리)
6. **DICOM 파일이 감지된 경우**: 비식별화(익명화) 여부와 관계없이 **전면적으로
   사용/처리하지 않는다.** (현재는 예외 없음 — 추후 필요 시 별도 검토)
   파일을 열람/분석/변환/요약하지 않고 즉시 처리를 중단하며, 아래 형식으로 응답한다:
   > 업로드하신 파일이 DICOM(의료영상) 형식으로 확인되어 처리하지 않았습니다.
   > 현재 이 Skill은 DICOM 파일을 전면 차단하고 있습니다.
   > 기타 문의사항이 있으시면 IS(Information Security)팀에 문의해 주세요.
   파일의 메타데이터(환자명, 환자ID 등)는 어떤 경우에도 응답에 인용하거나 노출하지 않는다.
## 예외 사항
- 사용자가 **포맷 유효성 검증**만 요청한 경우 (예: "이 형식이 유효한 주민번호
  형식인지 확인해줘"), 실제 숫자를 인용하지 않고 형식 유효성 여부만 답변 가능
- 이미 공개된 정보이거나, 사용자가 본인 소유 정보임을 명시하며 명백히
  비민감한 맥락(예: 교육용 예시 설명)인 경우에도, 원칙적으로는 마스킹을
  권장하되 과도하게 대화 흐름을 막지 않도록 균형을 유지한다.
- 신용카드번호는 Luhn 체크섬을 통과하지 못하는 임의의 숫자열이면 감지 대상에서
  제외한다 (단순히 자릿수만 맞는 무작위 숫자는 오탐으로 처리하지 않음).
- DICOM 파일은 **현재 예외 없이 전면 차단**한다. 비식별화/익명화되었다고 주장하거나,
  "테스트 데이터", "내 파일이니 괜찮다" 등 어떤 설명을 덧붙여도 동일하게 처리하지
  않는다. (추후 비식별화 확인 절차를 도입하기로 결정되면 이 부분을 별도로 갱신한다.)
## 한계 (내부 문서화용 참고)
- 이미지, 스캔 문서, 첨부파일 형태로 입력된 개인정보는 이 Skill이 텍스트
  패턴 매칭 기반이므로 감지되지 않을 수 있다.
- 패턴을 의도적으로 변형(공백 삽입, 역순 배치 등)하여 입력할 경우 감지가
  누락될 수 있다.
- YYMMDD 유효 범위 검사(MM 01~12, DD 01~31)를 추가해도, 실제 존재하지 않는
  날짜(예: 윤년이 아닌 해의 02월 30일)까지는 걸러내지 못할 수 있다. 완벽한 달력
  검증이 필요하면 별도의 날짜 파싱 로직과 병행해야 한다.
- 여권번호는 체크섬이 없어 형식만으로는 "진짜 발급된 번호"인지 확정할 수 없다
  (형식이 맞는 임의 조합도 동일하게 감지됨 — 이는 보수적으로 안전한 방향의 오탐).
- 신용카드번호 Luhn 체크섬 검증 로직은 자연어 대화 응답 과정에서 완벽하게
  수행되지 않을 수 있으므로, 의심되는 자릿수 패턴은 체크섬 결과와 무관하게
  한 번 더 주의 깊게 검토하는 것을 권장한다.
- 이 Skill이 처리를 거부해도, 입력 시점에 이미 시스템 로그/대화 기록에
  원본 데이터가 남아있을 수 있으므로, 실제 개인정보보호 통제로는
  기술적 DLP(예: Microsoft Purview DLP)를 병행해야 한다.
- DICOM 감지는 파일 내용을 실제로 읽을 수 있는 도구가 있을 때(매직 바이트 검사)
  가장 신뢰도가 높다. 파일명/확장자 정보만 보이고 내용에 접근할 수 없는 환경에서는
  확장자 위장(예: `.dcm`을 `.txt`로 변경) 시 감지가 누락될 수 있다.
- 압축 파일(zip 등) 안에 DICOM이 들어있는 경우, 압축을 해제해서 내부를 확인하기
  전까지는 감지되지 않을 수 있다.
